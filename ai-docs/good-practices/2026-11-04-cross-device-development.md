# 软件本体与插件协作的开发经验

日期：2026-11-04。范围：本轮 Synra 软件本体、共享核心、协议包及独立插件的协作开发。

这轮解决的配对、权限、弹层、设备连接和移动端导航问题，集中暴露了几个共同问题：同一件事由多个地方维护状态，把连接成功当成业务成功，以及页面生命周期与任务生命周期混在一起。
有效的做法是先明确用户流程，再确定每个状态、决定和资源由谁维护，让软件本体与插件通过共同契约协作。本文记录这些可以继续沿用的经验；具体插件实现和测试数量留在实施记录中。

## 1. 软件本体提供通用能力，插件承载业务体验

先划清职责，再决定在哪里增加页面或接口，能避免每接入一个插件就修改一轮主程序。

| 位置 | 应承担的职责 |
| --- | --- |
| 软件本体界面 | 设备与插件管理、权限决策、通用任务确认、取消、设置和诊断 |
| 宿主与原生页面容器 | 插件页面身份、窗口或 Activity、返回入口、平台生命周期接入 |
| 共享核心 | 配对与授权规则、连接、任务状态、协议检查和资源清理 |
| 平台适配器 | 操作系统能力的具体实现 |
| 独立插件 | 自己的业务页面、交互说明、业务逻辑，以及对通用能力的调用 |

本轮保留了这种分工：插件拥有自己的页面，宿主提供统一的打开、返回和授权流程；需要脱离界面也成立的规则进入共享核心。
插件管理页的“打开”负责进入插件，具体业务动作在插件内完成。宿主可以展示插件名称、任务和错误，但这些展示数据不应变成写死某个插件业务的理由。

以后接入新插件时，先判断现有能力能否组合完成需求。需要扩展通用能力时，沿接口、核心、平台实现和宿主接入补齐，业务体验继续由插件负责。

## 2. 配对码一闪而过：让明确同意驱动业务完成

原来的现象是：A 发起配对，配对码一闪而过，随后提示 B 没有接受；B 却已经显示“已配对”和“忘记”。
根因在于接收连接的 `Hello` 提前写入了 `paired_devices`，真正的配对请求随后又被“已经配对”检查拒绝。
双方都在更新界面，却依据了错误的完成时机。

修复时先把双方应该看到的状态写清楚：

| 阶段 | A：发起端 | B：接收端 | 配对关系 |
| --- | --- | --- | --- |
| 请求到达 | 显示本次配对码，等待对方确认 | 显示同一个配对码，可同意、拒绝或拉黑 | 尚未建立 |
| 等待操作 | 保持等待，可取消 | 保留请求，等待用户决定 | 尚未建立 |
| B 同意 | 收到完成结果后显示成功 | 完成确认与保存后显示成功 | 按配对流程建立 |
| 拒绝、拉黑或 A 取消 | 显示对应结果，结束本次请求 | 结束本次请求 | 不授予可用配对 |

随后统一实际执行路径：

- 移除握手阶段的配对写入，让连接建立与用户同意各自完成自己的职责。
- 监听器与命令处理复用同一个 `AppState.host`，让接收请求、用户回答和事件通知进入同一份配对状态。
- 配对提示放在应用根组件，由全局 store 驱动，切换页面后仍能回应。
- 拒绝也向对端发送明确答复；接受并保存后，再通知设备列表刷新。
- 防止较早的等待快照覆盖较新的完成事件，取消也进入实际任务流程。

有效的回归同时驱动真实 TCP 两端，检查同码、持续等待、同意、拒绝、撤回和拉黑；前端另覆盖全局提示与迟到响应。
“弹窗保持多久”因此成为业务状态的自然结果，无需增加显示延时。

可复用的方法是：**先为成功定义明确事实，再让两端界面显示这个事实。** 接通、收到请求、用户同意、保存完成，应有各自的含义。

## 3. 将配对、插件确认、能力授权和启用分开

这些状态服务于不同决定，界面需要分别表达：

| 状态 | 回答的问题 |
| --- | --- |
| 设备已配对 | 是否建立了这两个设备之间的配对关系？ |
| 插件已确认 | 用户是否明确允许这个插件运行？ |
| 能力已授权 | 插件能使用哪些能力、作用于哪些范围？ |
| 插件已启用 | 用户现在是否希望它处于启用状态？ |
| 本次操作已同意 | 对于需要逐次确认的动作，接收端是否允许当前请求？ |

零权限插件是一个有价值的边界案例。它显示“需要检查权限”，进入后却只有“无需权限”，并非漏了一组权限数据：清单确实没有请求能力，但界面没有确认入口，核心也把空授权集合当成不能批准。

修复后，空权限清单仍如实显示“无需权限”；尚未确认时，另提供“允许运行”，提交明确的空能力决定。
确认后，已经启用的插件可以运行；尚未启用的插件保持停用。安装、确认和启用各自保留语义。

权限界面沿用同样的原则：首次决策进入编辑，已有决定先查看再修改；新增权限不预选，支持部分授权，提交失败保留草稿。
后台执行仍复核当前授权，页面里显示过“允许”不能代替执行时的检查。

这种拆分让提示文字和下一步操作都能对应真实原因，后续插件也能复用统一流程。

## 4. 用真实协议修复第一处错误，同时校准预览和测试

权限页崩溃时，最早的 `denied is not iterable` 是直接线索；后续 `subTree`、`parentNode` 和组件更新警告是渲染中断后的级联症状。
有效的排查顺序是沿首条错误核对实际返回值，再复测关闭、切页和重开。

本次 Rust `serde` 会省略空列表，TypeScript 却将部分字段声明为必填，组件直接展开这些字段。测试和预览始终提供空数组，反而掩盖了生产数据形态。
修复覆盖了四个位置：

1. 共享 `@synra/protocol` 正确声明可省略字段，页面使用共享类型。
2. 调用方按字段语义处理缺省；请求权限来自清单声明，不从历史允许或拒绝记录猜测。
3. 假内核同样省略真实协议会省略的空字段。
4. 协议检查核对 Rust 可省略字段与 TypeScript 可选声明，并补充缺省字段的回归。

同类检查也发现了更新能力列表和动作候选列表的声明偏差。
可复用的经验是：修复跨语言契约时，把生产端、消费端、预览和测试夹具一起校准。类型检查的价值建立在声明符合真实数据之上。

## 5. 共享状态只有一条更新路径，页面负责读取

配对、设备、权限和通用任务会跨越多个页面。有效的组织方式是由核心维护业务事实，经 `src/events.ts` 的唯一订阅分发到 store，页面读取同一份状态。
命令返回值和全量快照也要遵守这套更新顺序。

本轮保留并补强了几项规则：

- 初始读取、重读和事件更新使用版本检查，旧请求晚到时不能回滚新状态。
- 事件出现缺口时重读权威快照；已知的诊断事件明确分发，避免每一帧都被当成未知事件触发设备重读。
- 控制台使用已有事件分发，不再建立第二个内核订阅。
- 业务状态与编辑草稿分开，临时隐藏页面不会丢掉用户尚未提交的选择。

这使设备列表、插件详情、全局提示和日志能够解释同一件事，也减少了重复读取及页面之间的状态漂移。
调试新功能时，先查事件是否进入现有分发、store 是否接收，以及旧响应是否可能覆盖它，通常比增加页面监听更有效。

## 6. 独立工作流拥有独立的展示与关闭路径

同步窗口瞬间消失、主界面被挤动、后续日志抽屉打不开，分别涉及组件归属、挂载容器和展示优先级。
同步窗口原先声明在详情抽屉正文里；协调器隐藏详情时，里面的同步窗口也被隐藏，但它仍登记为打开，形成了无法关闭的状态。

修复后的交互模式是：

- 详情与同步成为同级工作流，关闭同步后恢复原详情及上下文。
- 弹层使用 body Portal，抽屉关闭 push 位移，主布局保持原位。
- 协调器决定当前展示哪一层，同时保留被暂时遮住的工作流与草稿。
- 配对等决策、日志和全局查找有明确的打断与恢复规则，关闭后能回到原流程。

验证直接检查 Portal 中的实际 DOM、焦点和主界面尺寸，并走完“详情 → 同步 → 日志 → 恢复同步 → 恢复详情”。
只检查组件的 `open` 属性，无法证明用户看得见、点得到或关得掉。

移动端插件采用同样的所有权思路：独立 `PluginActivity` 承载页面，WebView 外提供“返回 Synra”，系统返回也由宿主处理。
插件网页加载或执行失败时，用户仍能回到主程序。桌面独立窗口与移动端页面可以有不同承载方式，共享的是宿主负责导航出口的规则。

界面样式也围绕操作关系统一：普通与紧凑控件采用一致尺寸，触控环境单独适配；常用动作常显，低频动作进入更多菜单；安装优先使用原生文件选择，高级路径输入按需展开。
这些改动与完整操作流程一起检查，才能判断用户是否能顺利完成任务。

## 7. 区分发现、在线和业务可用，沿读写路径排查连接

双方已经配对且软件打开，却显示离线；一端只有 `lan query`，另一端不断出现 `lan heard`，同步又报告连接拒绝。
这类现象需要逐步核实：收到发现公告、当前可达、已配对、插件可运行、业务请求完成，分别需要不同证据。

本轮沿地址的产生、保存和使用路径找到了实际问题：

- UDP 查询应回复实际的 UDP 来源地址，不能拿公告中的 TCP 监听端口作回程；重复查询也应回答。
- 多网卡广播使用接口的真实广播地址，不能假定所有网络都是 `/24`。
- 入站 TCP 的临时源端口不能覆盖对方声明的监听端口。
- 同步、传输和远程调用共用地址解析，优先读取近期发现的有效端点，再按规则回退到保存地址。
- 在线状态参考近期发现和有效会话，处理过期与离线公告；配对关系独立保留。
- 设备用 UUID 关联，名称只负责显示；发现阶段只知道 `desktop` 时保留这个类型，选择器也识别它。

回归使用独立 UDP 查询 socket 和真实 TCP 监听器，还覆盖旧端点关闭、发现新端点后重新请求插件清单。
重要经验是：**表里有地址，还要确认真实连接入口正在读取它。** 排查数据问题时，同时寻找写入方、读取方和失效条件。

## 8. 让取消、撤权和退出真正结束任务

界面关闭时，后台可能仍在拨号、等待确认或执行任务。稳定的交互要求每个任务有明确身份、所有者和结束路径。

本轮有效的处理包括：

- 在异步连接前后复核取消与授权，避免用户取消后又弹出迟到的确认。
- 将请求绑定到设备、插件、会话和授权版本，旧任务不能借新授权继续执行。
- 在产生实际效果的入口复核当前状态，并约束重复与乱序请求。
- 页面返回、进入后台、断连、撤权和插件停止时，按所拥有的任务释放资源；接收端也承担独立清理职责。
- 多线程状态发布与资源交接明确排序，避免旧通知覆盖新状态，或新任务接管时旧资源尚未释放。

例如，触摸板插件可以自行实现手势与页面说明，而本次电脑授权、停止入口和失去连接后的按键释放由宿主与核心共同保障。
这个局部例子说明，业务交互可以独立扩展，授权与生命周期仍能遵循软件本体的统一规则。

## 9. 验证完整用户路径，并说明证据覆盖到哪里

有效的验证针对用户可观察的结果，而非只断言内部函数返回成功：

| 验证层次 | 本轮值得保留的检查方式 |
| --- | --- |
| 协议与核心规则 | 缺省字段、零权限确认、同意前不完成、拒绝与取消有明确结果 |
| 界面与状态 | 旧响应不会覆盖新事件，关闭和重开可用，草稿与上下文可以恢复 |
| 真实弹层 | 保留 Portal，检查实际可见性、焦点、关闭入口和布局尺寸 |
| 双端网络 | 同时驱动两端，检查同码与等待、拒绝与撤回、地址更新和断连 |
| 实际插件包 | 经生产安装、确认、启用、页面身份与 RPC、真实 Wasm 进入共享服务 |
| 原生设备 | 单独检查对应系统的窗口、返回、实际平台效果及性能 |

完整插件包验收曾发现能力声明尚未进入安装许可集合，说明 SDK 调用能够编译，还需要检验 CLI 校验、清单安装和宿主执行是否使用同一契约。
接口扩展应沿 WIT、生成器、SDK、宿主与作者 CLI 一起核对。

测试替换最后一层平台适配器时，应明确它证明了调用与清理链路；实体设备效果仍需另行验证。
本轮回环网络、浏览器与包验收的结果各自记录，Android/卓易通及 Windows 原生实际操作的未覆盖部分也保留在实施记录中。

交付上，插件 SDK 与作者 CLI 固定到同一个已审查版本，提交锁文件，移除联调期本地覆盖后再次构建和校验。
开始工作先记录仓库基线，按本轮文件审查与提交，保留已有用户改动，格式化也限定范围。
安装包提供版本、架构、签名与校验信息；FTP 使用临时名上传、完整回读比较 SHA-256 后再改最终名。
这样，用户遇到的问题能对应到具体源码和交付物，后续复测也有一致起点。

## 后续开发可以沿用的顺序

1. 写出两端或宿主与插件各自看到什么、能做什么，以及什么事实代表完成。
2. 确定状态、授权、页面和资源的所有者，优先复用核心服务、事件分发与共享协议。
3. 连接正常流程，同时补齐等待、拒绝、取消、失败恢复和退出清理。
4. 从真实数据形态和真实入口验证，检查完整操作链及相邻工作流是否还能继续使用。
5. 固定跨仓库版本，核对实际交付物，并记录验证范围与可复用经验。
